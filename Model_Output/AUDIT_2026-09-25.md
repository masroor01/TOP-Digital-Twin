# TOP Digital Twin — Full Project Audit
**Date:** 2026-09-25
**Scope:** All 71 top-level scripts + 5 GEE automation scripts + weekly-refresh CI/local infra + web dashboard, deep line-by-line review, cross-checked against `Model_Output/MANIFEST.md`'s documented history.
**Method:** 8 parallel deep-review passes (data ingestion; satellite/GEE; M7/M8/M9 + drought/fertilizer/ONI layers; core modeling pipeline; panel/SDID experiments; layer-5 + diagnostics; escalation/validation; CI/web infra), each reading full files, checking against documented conclusions, and hunting specifically for the cross-file dedup bug class found and fixed in Script 14 on 2026-09-24.

**Headline:** No bugs found that are currently corrupting the live dashboard's actual price forecasts. Script 23's M6 feature set was checked explicitly against M7/M8/M9 and is clean — no undocumented layer leakage into production. The issues below are real, but they cluster in three places: (1) a validation-leakage pattern affecting model *selection* (not headline test metrics) that was fixed once but never propagated, (2) a silent data-contamination bug affecting potato's climate features outside the main modeling join, and (3) a cluster of documentation/reproducibility gaps (results that exist only as one-off interactive analysis, "live" scripts that quietly went stale, uncommitted work-in-progress).

## Findings, ranked by severity

### 1. [HIGH] Train/validation temporal leakage in Scripts 15, 15b, and 23 — not propagated from Script 12's own fix
**Files:** `scripts/15_Ablation_Study_M0_M4.py:693`, `scripts/15b_Tree_Model_Comparison.py:388`, `scripts/23_Train_Production_Models.py:315`

Script 12 (`12_ModuleB_RollingOrigin_MultiHorizon.py`) explicitly diagnosed and fixed this bug in its own file: filtering training rows by **origin** week only (`week_start <= t_end`) lets a row whose **target** (origin + h weeks) lands inside the validation window contribute to the fit. For h=26, a training row at `t_end` has a target ~6 months later — squarely inside the val window used for early stopping.

This fix was never back-ported. Scripts 15, 15b, and **23 (the production training script that drives the live dashboard)** all still use the origin-only filter. `15c_LSTM_Transformer_Comparison.py` and `17_TFT_Model.py` correctly guard against it (`target_date_hi` / restricting the source frame to `time_idx <= train_end_idx`).

**Impact:** this pollutes the early-stopping signal (tree-count selection), not the final TEST-set metrics directly — so headline RMSE/R²/MAPE numbers in `ablation_raw_results.csv` aren't proven wrong, but the deployed models' tree counts were picked using a contaminated validation signal. Worth fixing project-wide, prioritizing Script 23.

### 2. [HIGH] Orphaned pre-relocation potato zone data silently pollutes `crop_weekly_features.csv` and every potato paper figure
**File:** `scripts/14_Satellite_Climate_Features.py`, Steps 2–7

The 2000-2024 historical zip/CSV extracts for potato zones P1-P3 are still under their **old** identity (`P1_Agra`, `P2_Farrukhabad`, `P3_Jalandhar`) — confirmed present across all 5 raw source folders (era5, era5_topup, chirps, modis, s2). Script 14's own comment already calls this data "orphaned, not usable for the new sites," but the code never filters it out. Because Step 6's zone skeleton is built from whatever `zone_id`s appear in the loaded data (not Script 16's canonical 17-zone list), these 3 phantom zones survive into `zone_weekly_features.csv`, and Step 7's `crop_weekly_features.csv` averages **across every zone of a crop** — so potato's crop-level climate average for every week 2000-2024 silently blends in Agra/Farrukhabad/Jalandhar alongside the real Bardhaman/Darjeeling/Diamond Harbour/Dehradun zones. This also feeds every potato figure in Step 10.

**Good news:** `market_zone_features.csv` — the join documented as preferred for modeling — is unaffected, since it's built by merging Script 16's `zone_assignment.csv` (which only ever contains the 4 current potato zone_ids), not from the raw zone list directly. **If production scripts consistently use `market_zone_features.csv`, trained models are unaffected**; the fallback dataset and every potato paper figure are not.

**Fix:** filter every raw-load loop in Steps 2–5 to zone_ids present in Script 16's `ZONES` dict (or explicitly drop `{P1_Agra, P2_Farrukhabad, P3_Jalandhar}`) before building `zones_meta`.

### 3. [HIGH] The project's actual trusted significance methodology for M7/M8/M9 exists only as MANIFEST.md prose — never saved as code
**Files:** `scripts/55_DM_Test_M6_vs_M7.py`, `60_DM_Test_M6_vs_M8.py`, `64_DM_Test_M6_vs_M9.py`

Scripts 55/60/64 each implement *only* the flawed per-market DM test (hundreds of markets scored by one shared fold-level model, presented as independent significance — the pseudo-replication bug this project already found and corrected for). The corrective fold-level pooled-MSE binomial test — the actual methodology the project trusts for the M7/M8/M9 wiring decisions — exists **only as "ad hoc analysis, no saved script" rows in MANIFEST.md**, run interactively at least 5 separate times (M7 initial, M7 fold-1-fix, M8, M9, M9 CV-extension), each requiring a manual backup/restore of `dm_market_level_predictions.csv`.

**Consequence:** if anyone re-runs Script 55/60/64 today without independently knowing to also do the unscripted follow-up, they get the already-debunked inflated per-market picture. Recommend extracting the fold-level check into a real, reusable script (e.g. `65_FoldLevel_Significance_Test.py`).

**Related:** Script 60's own inline interpretation guide (lines ~204-209) tells the reader that near-0% byte-identical predictions across folds means "per-market counts are trustworthy" — this is now known to be wrong (M8's fold-level check *did* come back clean, and the per-market counts were *still* pseudo-replicated artifacts). Script 60 should be corrected or flagged; Script 64 (written later) already hedges correctly.

### 4. [HIGH] Scripts 43/45 ("Live" forecast validation) are dead — hardcoded stale dates, zero MANIFEST history
**Files:** `scripts/43_Live_Onion_Forecast_Validation.py`, `scripts/45_Live_Tomato_Forecast_Validation.py`

Both hardcode a single `TARGET_WEEK` (2026-07-27 for onion, 2026-08-03 for tomato) — 8-9 weeks stale as of today (2026-09-25). Both assert this matches `reference_rows.csv`, which has almost certainly moved past that date since Script 23 was re-run 2026-09-07 — so running either today would likely throw immediately rather than silently validate stale data, but neither has any rolling/dynamic date logic, and **neither has ever appeared in MANIFEST.md** (confirmed via grep — every other script 40-50 does). This is the clearest instance in the whole codebase of a script quietly going stale and being abandoned without anyone noticing. Either wire these into a recurring cadence with a dynamic `TARGET_WEEK`, or retire them explicitly.

**Related gap:** Script 44 (`44_Pipeline_Sanity_Check.py`), which is otherwise the strongest defensive-engineering script in the project (8 real historical-incident checks with PASS/WARN/FAIL + exit codes), has no check that would have caught this — no "is this Live script's target date still recent" check exists anywhere. Worth adding.

### 7. [MEDIUM] Scripts 39/39b — placebo units' donor pools include the actual treated crop, undocumented
**Files:** `scripts/39_SDID_Stacked_MultiEpisode_EventStudy.py`, `39b_SDID_Arrivals_Stacked_MultiEpisode_EventStudy.py` (inherited from `scripts/31_Synthetic_DID_Policy_Effect.py`)

For the real onion ATT, the donor pool is correctly tomato+potato only. But for the **placebo units** (tomato, potato — whose ATTs form the "null" band onion's result is judged against), the donor pool includes **onion itself**, the crop actually under the export ban at that date. This can bias the null band (typically compressing it) rather than giving a clean untreated comparison — directly relevant to the headline "onion separates from placebo band in 10/13 post-ban bins" claim. Otherwise the event-window mechanics are correct and well-documented; this one issue is the sole undocumented gap in an otherwise unusually self-critical set of scripts (which do candidly document *other* known limitations like pre-period contamination from earlier bans).

### 8. [LOW-MEDIUM] CHIRPS pentad-vs-ISO-week misalignment — known, still unfixed
**File:** `scripts/14_Satellite_Climate_Features.py`, Step 3 (confirmed via `scripts/gee_auto/02_chirps_topup.py`'s own docstring, which flags this as a deliberately-untouched known bug)

CHIRPS pentads (5-day windows anchored to calendar-month boundaries) don't align to Monday-start ISO weeks; a pentad straddling a week boundary gets fully counted in one week and misses the other. Pre-existing, documented, not newly discovered — flagging because it affects rainfall features used in every crop model and was raised again independently by this audit.

### 9. [LOW-MEDIUM] Script 51 (VEDAS drought) — plausible cache-poisoning hazard for not-yet-published fortnight dates
**File:** `scripts/51_Drought_Trigger1_VEDAS_Layer.py`

`CACHEABLE_STATUSES = {'ok', 'empty_response'}` permanently caches an empty response, reasoning that "empty means invalid calendar date." But the date grid includes the *current* season's future fortnight dates too. If the server returns the same empty response for both "invalid date" and "valid date, not published yet," a run before data lands would permanently poison the cache for a date that will have real data weeks later — and the automated weekly refresh would never pick it up. Worth an empirical check (query a not-yet-arrived fortnight date, then again after it occurs) before the next Kharif season closes.
